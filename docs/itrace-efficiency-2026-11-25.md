# itrace 消费效率优化与实机对照

2026-11-25，fuxi `282eb4e4`。优化逐条 JSON 编码、重复检查和 ringbuf 唤醒。事件 ABI、JSON 字段、寄存器增量及丢失恢复语义保持一致，ringbuf 仍为 32 MiB。

## 固定 CPU / 频率的结果

旧、新版分别运行三轮，目标固定 CPU 4、消费者固定 CPU 5，所在簇临时设为 1.92 GHz。每组 250000 次调用、600 万条动态指令，17 个唯一点位。验证 taskset 的实际允许 CPU，每版结束核对实际频率，最终恢复原上下限 1920000 / 2592000 kHz。

有效接收速度采用 `received / ready到退出的完整时间`，包含排空、主机控制和关闭成本。表中为三轮中位数；丢失率按三轮命中总数计算。旧版存在丢失的结果只是收到的有效记录速率，不代表完整轨迹。

| 模式 | 优化前 接收条/s | 优化后 接收条/s | 变化 | 丢失率 前→后 |
| --- | ---: | ---: | ---: | ---: |
| PC 汇总 | 521,750 | 782,784 | +50.0% | 0.000% → 0.000% |
| 寄存器增量汇总 | 365,958 | 614,526 | +67.9% | 0.000% → 0.000% |
| PC JSONL（设备 /dev/null） | 715,160 | 771,432 | +7.9% | 14.610% → 0.000% |
| 寄存器增量 JSONL（设备 /dev/null） | 592,921 | 596,692 | +0.6% | 7.079% → 0.000% |

新版四项均完整收到每组的 600 万条。固定核频仍不能完全隔离缓存、温度和后台负载，三轮顺序 A/B 的百分比不应外推为所有指令和设备的保证。

## 实现与唤醒开销

- `b8e99c5`：按实际运行时 PC 缓存转义后的固定 JSON 字段，减少逐条分配、格式化和转义；寄存器增量只遍历变化位。生命周期/时长最多每 256 条检查一次，count 和停止信号仍逐条检查；解码复制后即释放 ring slot。
- `11eb203`：BPF 复用已有线程的第一次状态查询，消除每条命中的第二次 map 查询；新线程初始化、序号和退出清理保留原逻辑。
- `9a0ca9f`：第一条立即通知，之后每 64 条批量唤醒；稀疏尾部以 5 ms poll 超时补收。每条命中仍生成记录，不对采集节流。5 ms 是轮询间隔，阻塞输出和调度仍可能增加延迟。
- `ff23f0a` / `bd36ec8`：基准区分设备 `/dev/null`、ADB 到主机 `/dev/null` 和保存文件，记录完整消费时段，支持固定 CPU 和选择独立版本产物。

固定核频测试发现，只加快消费端会让它更频繁地清空 ringbuf 并睡眠，反而触发大量唤醒。中间版本每组 600 万条 PC JSONL 发生约 33 万次主动上下文切换，有效接收速度从旧版约 71.5 万降到约 54.7 万条/s。批量通知后该项约 7.4 万次，速度恢复并超过基线；中间版本数据保存在 after-controlled 报告中，没有混入最终结果。

缓存属于一次不可变 Plan，按 cookie/实际 PC 区分同文件偏移的私有明文别名；JSON 字符串由锁定版本 serde_json 的 raw_value 功能编码，没有增加依赖包。没有增加输出线程、额外事件队列或新传输协议。

## 原规模长批次

普通 Android 调度下，新版每项三轮，每轮 2400 万条，合计 288,000,000 次命中、收到 288,000,000 条。全部收到，无 ring 丢失或序号缺口。

JSONL 输出到设备 `/dev/null`，保留格式化开销但排除 USB/主机输出。汇总模式仍采集和校验每条记录，只省去逐条格式化。

| 模式 | 目标命中 insn/s | 有效接收条/s（含排空） | 丢失率 |
| --- | ---: | ---: | ---: |
| PC 汇总 | 1,124,819 | 1,109,187 | 0.0000% |
| 寄存器增量汇总 | 883,140 | 873,524 | 0.0000% |
| PC JSONL（设备 /dev/null） | 1,507,069 | 1,461,431 | 0.0000% |
| 寄存器增量 JSONL（设备 /dev/null） | 1,203,215 | 1,185,510 | 0.0000% |

一次 USB 链路重建期间，第三轮 PC JSONL 的远端会话提前结束，未形成有效样本，boot ID 不变且未见新增 tombstone。保留 final-local-interrupted 原始失败报告，补跑剩余两项；表中每项三轮来自有效完成的样本，final-local 聚合记录逐项注明来源，未把中断尝试算作通过。具体断开原因未获完整 fixture stderr 证实，现已补充保留该诊断。

普通调度没有固定 CPU 和频率，不能用其前后数字代替上面的受控对照。优化前设备端 JSONL 基线三轮合计 PC/寄存器分别丢失 15.103% / 46.577%，中间版本四项合计 2.88 亿条零丢失；这些原始样本均保留。

## ADB 输出限制

最终版 PC/寄存器 JSONL 经 ADB 输出各复验一组 2400 万条，目的为确认链路边界；旧版的三轮结果只作量级参考，不能用细小百分比变化推断因果。

| JSONL 模式 | 旧版三轮丢失率 | 最终版单组丢失率 |
| --- | ---: | ---: |
| PC JSONL | 92.258% | 93.079% |
| 寄存器增量 JSONL | 94.643% | 96.799% |

ADB 满速输出仍有严重瓶颈，不能声称此次优化解决了传输能力限制。保留全部 JSON 字段后，格式化、USB 和主机接收的独立贡献尚未完全拆分。旧的短突发零丢失也不能外推为持续满速输出保证。

## 正确性与设备状态

- 40 项主机测试、fmt、用户态/ABI 与 eBPF clippy、Android/eBPF release 构建通过。缓存用例覆盖引号、反斜杠、换行、Unicode、动态字段和同 inode 不同私有明文。
- 最终版设备 smoke 包含原有 601 条精确路径事件，以及 48 条在停止 tracer 前已收到的稀疏尾部事件，共 649 条；还覆盖线程、迁移、81 点、跨页、异常、拒绝条件、精确 count 和目标退出。
- 私有解密页 itrace 两轮及普通 uprobe 的寄存器/内存/栈/count=3 通过。checkpoint 2400 条零丢失，主动 SIGSTOP 消费者后仍可检测缺口并通过完整快照恢复后续寄存器状态，无法恢复已经丢失的事件。
- 本轮不修改或刷写内核，boot ID 与 boot_a 哈希不变，当前仍运行此前的新内核。CPU 频率设置已恢复，夹具进程已退出；保留日志未见 BUG/Oops/panic；USB 重连复现了既有 DWC3 enable_irq 告警，内核日志发生环形覆盖，不能声称本轮零告警。

## 复现和记录

分别构建并保存旧、新版 amtracer 和 BPF 对象。频率是外部测试设置，须保存和恢复原限制；命令本身只指定 CPU 亲和性：

```sh
python3 tests/instruction_bench.py --serial 282eb4e4 \
  --tool-dir /path/to/version-artifacts --target-cpu 4 --tracer-cpu 5 \
  --json-sink device-null --seconds 9 --repeats 3 --event-rates 0 \
  --unpaced-rounds 250000 --modes baseline,pc,regs,pc-json,regs-json \
  --report artifacts/controlled.json
```

不节流时 `--seconds 9` 仅决定主机等待上限，不是固定 9 秒采样。长批次使用 rounds=1000000；`--json-sink host-null` 测包含 ADB 的输出。

完整报告、stderr、命令、频率恢复记录和三版产物位于本地 `artifacts/efficiency-20261125/`。报告的 Git HEAD 标识测试仓库，所选二进制以独立 SHA-256 识别。CPU ticks/上下文切换覆盖采样窗口，不包括所有末尾排空开销。各轮计数、完整耗时、版本与记录哈希见 [验证清单](validation-itrace-efficiency-2026-11-25.json)。二进制和大量原始输出不进入 Git。
